# PostgreSQL (Neon) + EF Core: setup, data migration, deployment

The API now uses Entity Framework Core with PostgreSQL (Npgsql). Dapper and SQLite
are no longer used by the API. `DATABASE_OPERATIONS.md` describes the old SQLite setup and is obsolete.

## 1. Configuration

The API reads the connection string from, in this order:

1. `ConnectionStrings:DefaultConnection` (user-secrets, or the `ConnectionStrings__DefaultConnection` env var)
2. the `DATABASE_URL` environment variable

Both a URL (`postgresql://user:password@host/dbname?sslmode=require`, what Neon shows) and a
Npgsql string (`Host=...;Database=...;Username=...;Password=...`) work. Remote hosts default to TLS.
If nothing is configured the API stops at start-up with a message naming `DATABASE_URL`.
No credentials are stored in the repository.

On start-up the API applies pending EF Core migrations (additive; it never drops or recreates tables).
Disable with `Database__MigrateOnStartup=false`.

## 2. Create the Neon database

1. neon.tech -> create a project (Free) -> note the database name (default `neondb`).
2. **Connect** -> copy the connection string. Prefer the **direct** (non-pooler) host (no `-pooler` in the
   name) for `DATABASE_URL`: EF migrations take an advisory lock, which PgBouncer's transaction pooling
   does not support. The pooled host is fine for the running app only if you set `Database__MigrateOnStartup=false`
   and run migrations from your machine with the direct string.
3. The `citext` extension is created by the first migration (Neon allows it).

## 3. Apply the schema (from your machine)

```powershell
cd LibraryManagement\LibraryManagement
$env:DATABASE_URL = '<neon connection string>'
dotnet ef database update          # applies InitialPostgres
```

`dotnet ef migrations add <Name>` creates future migrations. A plain SQL version of the schema is in
`database/postgres_schema.sql` (idempotent, generated by `dotnet ef migrations script --idempotent`).

## 4. Copy the existing SQLite data (one time)

The tool reads a *copy* of the SQLite file (the original, including its `-wal`, is never modified), refuses to run
if any PostgreSQL table already has rows, keeps the original IDs, copies everything in one transaction, resets the
identity sequences, verifies row counts and keys, and only then commits.

```powershell
$env:DATABASE_URL = '<neon connection string>'
# rehearsal: does everything, verifies, rolls back
dotnet run --project LibraryManagement.SqliteToPostgres -- --sqlite LibraryManagement\Data\application.db --dry-run
# the real copy
dotnet run --project LibraryManagement.SqliteToPostgres -- --sqlite LibraryManagement\Data\application.db
```

Stop the running API first so the SQLite file is not changing while it is copied.
Admin accounts exist only in this data (the application has no seeding), so do this before first use.

## 5. Run locally

```powershell
$env:DATABASE_URL = '<connection string>'
$env:Jwt__Key = '<long random secret>'
dotnet build LibraryManagement\LibraryManagement.sln
dotnet run --project LibraryManagement\LibraryManagement
dotnet test LibraryManagement\LibraryManagement.Tests            # SQLite in memory
$env:TEST_DATABASE_URL = 'postgresql://postgres:pw@localhost/postgres'   # optional: same tests on real PostgreSQL
dotnet test LibraryManagement\LibraryManagement.Tests            # creates and drops a throw-away database
```

## 6. Render

Web service from the repo (Docker, existing `LibraryManagement/Dockerfile`). Environment variables:

| Variable | Value |
|---|---|
| `DATABASE_URL` | the Neon connection string (secret) |
| `Jwt__Key` | a long random secret (the key in `appsettings.json` is a development placeholder) |
| `ASPNETCORE_ENVIRONMENT` | `Production` |

Render injects `PORT`; the Dockerfile already binds to it. Neon's free compute suspends when idle; the first
request after that waits for it to wake (the connection timeout is 30 s and transient failures are retried).
